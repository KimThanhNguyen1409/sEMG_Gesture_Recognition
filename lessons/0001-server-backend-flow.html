Bài 0001: Giải phẫu Luồng Backend của sEMG C Server

Trong hệ thống của nhóm ní, file Server/src/main.c đóng vai trò là bộ não trung tâm ở tầng Backend: nó đứng giữa Mosquitto MQTT Broker và Model MLP TensorFlow Lite. Toàn bộ quá trình từ lúc nhận gói tin của ESP32 đến khi ra quyết định cử chỉ chỉ diễn ra trong vài micro-giây mà không dùng bất kỳ lệnh cấp phát động (malloc) nào.

Tài liệu gốc khuyên đọc: Eclipse Mosquitto Client C API (mosquitto.h) & TensorFlow Lite C API Header Specification.

1. Vòng đời 2 Pha của Server C (Init vs Runtime)

Để chạy 24/7 trên Windows mà không bao giờ bị tràn RAM (Memory Leak), main.c tách bạch 2 pha:

  • Pha Khởi tạo (main() + ml_runtime_init()): Chạy đúng 1 lần duy nhất khi bật chương trình. Nó nạp trọng số của semg_mlp.tflite (hoặc tensorflowlite_c.dll), khởi tạo biến toàn cục tĩnh g_ctx và kết nối vào MQTT Broker ở cổng 1883.
  • Pha Chạy thực (Event Loop mosquitto_loop()): Nằm chờ gói tin từ ESP32. Mỗi khi có gói tin tới topic semg/v1/+/features, thư viện Mosquitto tự động kích hoạt hàm callback on_mqtt_message() chạy qua 5 trạm xử lý nối tiếp dưới đây.

3. Giải thích Chi tiết Từng Trạm trong Code C

Trạm 1: Bóc tách JSON không cấp phát động (parse_feature_payload)

Thay vì gọi malloc tạo cây đối tượng JSON mỗi 25ms, hàm parse_feature_payload() chép bản tin vào mảng tĩnh char buf[1024] trên Stack, dùng strtof() quét trực tiếp 15 số thực giữa cặp ngoặc vuông [...] nạp thẳng vào ctx->raw_features[15].

Trạm 2: Chuẩn hóa Z-Score (semg_normalize_features)

Vì lúc huấn luyện trên Python ta đã chuẩn hóa (X_train - mean) / std, nên ở C ta dùng đúng 2 mảng hằng số trong inc/model_params.h để đưa 15 đặc trưng về cùng thang đo trước khi vào mạng nơ-ron.

Trạm 3: Suy luận Dual-Engine (ml_runtime_infer)

Server ưu tiên kiểm tra xem có file tensorflowlite_c.dll cạnh semg_server.exe không. Nếu không có, nó tự động chạy hàm mlp_infer_builtin() tính trực tiếp 3 tầng Dense(64, ReLU) → Dense(32, ReLU) → Dense(4, Softmax) bằng trọng số trích xuất từ semg_mlp.tflite trong inc/tflite_weights.h.

Trạm 4 & 5: Chống nhảy nhãn (post_process_vote) & Phát lệnh MQTT

Nếu độ tự tin lớn nhất best_prob < 0.75f, Server ép nhãn về 0 (RESTING) để tránh cử động nhầm khi cơ tay mới hơi căng. Sau đó, nhãn phải xuất hiện đồng nhất trong cả 3 cửa sổ liên tiếp (vote_buf[3]) và khác với lệnh vừa gửi trước đó (stable_cls != ctx->last_published_gesture) thì Server mới gọi mosquitto_publish() bắn xuống thiết bị đích.

4. Kiểm tra Nhanh (Retrieval Practice)

Câu 1: Trong post_process_vote(), chuyện gì xảy ra nếu cử chỉ có xác suất cao nhất chỉ đạt 0.60 (nhỏ hơn ngưỡng 0.75)?

Câu 2: Nếu người đeo giữ nguyên động tác FIST suốt 5 giây (200 gói tin liên tiếp đều ra FIST), Server sẽ publish bao nhiêu gói lệnh xuống End Device?
